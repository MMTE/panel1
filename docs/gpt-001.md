# Panel1 Practical Roadmap Report

> Date: March 2026
> Audience: founders, CTO, engineering, product
> Goal: turn the current codebase into a shippable product with a realistic execution plan

## 1. Snapshot

Panel1 has a strong architecture direction and the right product ambition, but it is still in a hybrid migration state.

- Vision is clear: modular monolith, vertical slices, module-owned schema/routes/services/jobs/UI.
- Runtime exists: `@panel1/core` and `@panel1/types` are a good foundation.
- Proof of concept exists: `modules/support` and `modules/audit`.
- Product reality is still mostly legacy: backend is largely Express + tRPC, frontend is still hardcoded and typed against the legacy router.

## 2. Current Reality

### What is good

- `ARCHITECTURE.md` gives a coherent north star.
- `packages/core` already has loader, services, events, filters, DB, and module context primitives.
- `modules/support` and `modules/audit` prove that domain code can move into vertical slices.

### What is risky

- Frontend still depends on legacy `AppRouter` types and legacy tRPC patterns.
- `support` and `audit` are migrated on the backend, but parts of the frontend still expect old tRPC namespaces.
- Admin routes and navigation are still hardcoded.
- Old plugin UI system is now a stub, but many pages still render `PluginSlot`.
- Core module runtime is not fully production-hard yet:
  - jobs are registered but not fully executed by the new module runtime
  - module DB boot collects schema but does not yet represent a complete migration story
  - Hono module auth, tenancy, and permission patterns are not yet as mature as legacy tRPC middleware
- Permission naming is split between legacy admin names and new module names.

## 3. Main Product and Engineering Conclusion

This project should not optimize for "add more modules fast".

It should optimize for:

1. Stabilize the migration seam.
2. Harden the module platform.
3. Ship one real modular slice end to end.
4. Then move core revenue domains in order.

If the team expands feature surface before fixing the seam between legacy and modular systems, delivery speed will slow down and bugs will increase.

## 4. The Immediate Priorities

### Priority 1: Stop contract drift

The top issue is contract mismatch between frontend and backend.

- Web still uses legacy tRPC typing and hooks.
- Support and audit are now module-backed domains.
- The repo needs one explicit rule for each domain:
  - legacy tRPC
  - modular REST/Hono
  - temporary bridge

### Priority 2: Normalize auth, tenant, and permission rules

Before large migrations continue, the team needs one shared model for:

- authenticated request handling
- tenant context resolution
- permission naming
- permission enforcement across legacy and module APIs

### Priority 3: Make the module runtime reliable

Before moving billing, payments, subscriptions, and provisioning, the platform must support:

- real job execution
- real module boot lifecycle
- predictable error handling
- shared auth middleware for module routes
- operational visibility

### Priority 4: Prove one complete slice

Support and audit should become the first fully credible modular slice, not just backend migrations.

That means:

- API contract is stable
- admin pages use the correct contract
- permissions work
- empty/loading/error states are real
- workflows are testable

## 5. Recommended Roadmap

## Phase 0: Stabilize the Seam

Target: 1-2 weeks

Outcome:
- Every domain has a single clear API ownership path.
- Frontend no longer points at removed or unsupported contracts.

Work:
- define domain ownership matrix
- fix support and audit contract drift
- decide bridge strategy for any domain mid-migration
- standardize permission naming or define mapping layer
- add CI checks for contract drift

## Phase 1: Harden the Module Platform

Target: 2-4 weeks

Outcome:
- `@panel1/core` is strong enough for real business domains.

Work:
- make module jobs executable and observable
- improve module DB/migration flow
- add shared Hono auth/tenant/permission middleware
- add shared error handling and request logging
- define module startup/shutdown lifecycle clearly
- add integration tests for boot and runtime behavior

## Phase 2: Ship Support and Audit Properly

Target: 3-5 weeks

Outcome:
- first real modular product slice is usable and stable

Work:
- migrate support admin pages to the supported module API
- migrate audit admin page to the supported module API
- either implement or hide unfinished support surfaces
- add integration tests for support and audit workflows

## Phase 3: Build the Revenue Path

Target: 4-8 weeks

Outcome:
- one real commercial workflow works from product to payment to active service

Recommended order:

1. catalog
2. billing
3. payments
4. subscriptions
5. provisioning

Reason:
- this is the shortest path to a real sellable system
- provisioning should sit after subscription and payment lifecycle are trustworthy

## Phase 4: Modernize the Frontend Shell

Target: after the first modular slice is stable

Outcome:
- route/nav wiring cost drops
- adding modules becomes cheaper

Work:
- dynamic route registration
- dynamic nav registration
- generated API client from OpenAPI
- removal of legacy plugin UI stubs and hardcoded shell wiring

## 6. Proposed Epics

### Epic 1: API Contract Stabilization

Goal:
- remove ambiguity between legacy and modular APIs

Issues:
- define domain ownership matrix
- remove unsupported frontend dependencies on missing tRPC namespaces
- choose bridge pattern for in-flight migrations
- add API contract validation in CI

Done when:
- no frontend page relies on removed backend contracts

### Epic 2: Auth, Tenant, and Permission Consistency

Goal:
- one access-control model across the platform

Issues:
- define canonical permission naming
- create mapping from legacy admin permissions to module permissions
- add shared middleware for Hono routes
- standardize tenant extraction and validation

Done when:
- migrated domains do not invent their own auth or permission behavior

### Epic 3: Module Runtime Hardening

Goal:
- make `@panel1/core` production-capable

Issues:
- implement executable module jobs
- improve module schema/migration lifecycle
- add shared error handling and telemetry
- define runtime lifecycle and health behavior

Done when:
- a module can own data, routes, jobs, and lifecycle without ad hoc glue

### Epic 4: Support Module End-to-End

Goal:
- make support the first real modular product slice

Issues:
- migrate support admin UI to supported API contract
- implement ticket detail, reply, assign, and status flows cleanly
- decide alpha scope for knowledge base, automation, and agents
- add support integration tests

Done when:
- support works end to end without depending on removed legacy paths

### Epic 5: Audit Module End-to-End

Goal:
- make audit reliable and usable as a platform capability

Issues:
- migrate audit UI to module API
- define standard audit events across domains
- implement export and retention as real operations
- add audit workflow tests

Done when:
- audit logs are part of normal product operations, not a side feature

### Epic 6: Revenue Path MVP

Goal:
- create a minimal but real commercial workflow

Issues:
- migrate catalog into modular path
- stabilize billing and invoice lifecycle
- stabilize payment processing lifecycle
- stabilize subscription lifecycle
- connect provisioning to paid/active subscriptions

Done when:
- one product can be sold, paid for, activated, and supported

### Epic 7: Frontend Shell Modernization

Goal:
- reduce migration tax and future feature wiring cost

Issues:
- dynamic admin route registration
- dynamic navigation registration
- OpenAPI aggregation and client generation
- removal of hardcoded admin-only shell assumptions

Done when:
- adding a module page no longer requires editing multiple shell files

### Epic 8: Quality and Release Readiness

Goal:
- make releases predictable

Issues:
- add module-level integration tests
- add smoke tests for sign-in, support, audit, billing flow
- define alpha release checklist
- add better seed data and local environment confidence

Done when:
- release readiness can be measured, not guessed

## 7. Recommended Issue Order

This is the execution order I would use:

1. domain ownership matrix
2. support and audit contract fix
3. permission normalization plan
4. shared Hono auth/tenant middleware
5. module runtime hardening for jobs and lifecycle
6. support UI migration
7. audit UI migration
8. support and audit integration tests
9. catalog migration
10. billing migration
11. payments migration
12. subscriptions migration
13. provisioning migration
14. frontend shell modernization

## 8. Product Scope Advice

For the next milestone, do not market the platform as fully extensible or broadly complete.

Position it as:

- modern billing and provisioning platform in active build
- strong modular architecture foundation
- first modular domains live
- focused alpha path toward support, audit, catalog, billing, payments, subscriptions, and provisioning

Hide or defer unfinished surfaces if they are not part of the next milestone.

## 9. Success Criteria for the Next Milestone

The next milestone should be considered successful if:

- support and audit are fully usable through supported APIs
- module runtime is stable enough for the next core domain migration
- one revenue path is clearly defined and under implementation
- the team has a disciplined migration order instead of parallel architectural churn

## 10. Final Recommendation

Panel1 is promising, but the next win is not more breadth.

The next win is coherence.

Make the system agree with itself:

- one contract per domain
- one access model
- one migration order
- one credible end-to-end slice

Once that is done, the roadmap becomes much safer and much faster.
